# Fantasy Frontiers V6 — UI、玩法与音效一体化体验计划

> 状态：V6 技术切片已实施并通过自动化验证；真人试玩、真实设备、Hard 人工通关与最终数值冻结仍未完成。
> 日期：2026-09-22。
> 阶段：Vertical Slice → Production Readiness。
> 依据：当前工作区源码、[V5 方案与实施记录](../v5/plan.md)、[V5 数值基线](../v5/balance-design.md)及现有自动化证据。
> 目标：把 V5 的“可编辑、可运行、可模拟”框架，提升为玩家能够看懂、做决定、感受结果并愿意重试的完整塔防体验。

> 2026-09-22 工坊补充实施：地图工坊已从只编辑 12×8 空间布局扩展为完整关卡创作闭环，支持敌军波次、受控基准波次、地图与波次联合校验、同一 Game Core 隔离试玩、本地 JSON 往返，以及默认关闭的服务器草稿同步、乐观锁校验和不可变发布。生产入口与试玩返回均改为尊重 Vite `BASE_URL`，不再跳离 `/fantasy-frontiers/`。公共 UGC、任意数值和 AI 坐标仍不在范围内。

## 1. 执行摘要

V6 不再以增加页面、世界或美术数量作为完成度指标。三个方向必须共同服务同一条玩家体验链：

```text
看懂威胁 → 形成方案 → 部署防线 → 听见/看见结果 → 理解成败 → 调整并重试
```

V6 的玩家承诺：

> **玩家能在开波前理解威胁，在战斗中确认每座塔的作用，在失败后知道下一次应该改变什么。**

优先级：

1. 先用一关完成 UI、玩法、音效的端到端体验切片。
2. 再验证三类关卡是否产生不同决策，而不是同一套路换难度。
3. 最后扩展到大厅、世界选择、编辑器和移动端适配。

V6 不新增塔或敌人种类，不增加英雄、技能树、装备、抽卡、多人、排行榜或长期养成。现有 4 塔、4 敌人和三关基准战役足以验证核心体验。

## 2. 证据基线

### 2.1 已确认

- V5 已建立固定地图、显式 `WavePlan`、确定性 Game Core、Simulator、Metrics 和内部地图编辑器。
- 玩家战斗、编辑器试玩与自动评估使用同一套 Game Core 规则。
- 战斗已有生命、金币、波次、塔选择、升级、暂停、倍速和下一波文字简报。
- 已有建造、升级、受击、漏怪、波次开始等视觉反馈，但反馈分散在 `main.ts` 与 Phaser Scene 中。
- 设置页存在主音量、音乐和音效滑杆，并保存到浏览器本地设置。
- 当前源码没有真正的音乐/SFX 播放管理器，音量设置尚未驱动音频输出。
- V5 自动实验显示：Easy/Medium 对部分机器人偏宽松，Hard 会击败现有全部机器人；这不能替代真人可玩性结论。
- `main.ts` 同时承担页面流、战斗接入、HUD 更新、设置和大量反馈编排，继续直接堆 UI/音频逻辑会放大维护风险。

### 2.2 合理推断，仍需验证

- 玩家可能能完成建造，却不一定理解“为什么这个位置或塔型有效”。
- 下一波文字简报提供了信息，但在移动屏幕上可能与操作、战场和常驻 HUD 争夺注意力。
- 没有真实音效时，输入确认、攻击类型、基地受损和波次节奏缺少重要感知通道。
- 当前失败结果能显示统计，但不一定足以把失败原因转化为下一局策略。

### 2.3 未知

- 目标玩家的首局理解率、首次失败位置、主动重试率和三种关卡的真实通关策略。
- 真实手机上的字体物理尺寸、安全区、触控误操作、音频延迟和扬声器可辨识度。
- Hard 是否存在合理的人类通关方案。
- 不同浏览器、后台切换和系统静音状态下的音频恢复表现。

## 3. V6 设计支柱与反支柱

### 3.1 设计支柱

1. **读得懂**：入口、路线、威胁、塔的职责和资源状态在需要决策时清楚出现。
2. **选得出**：位置、塔型、升级和纠错形成可解释取舍，不是固定脚本。
3. **感受得到**：建造、攻击、控制、击杀、漏怪和胜负都有一致的视觉与听觉因果。
4. **败得明白**：结果页基于真实事件指出关键失守波次、入口和资源行为，不使用虚构建议。
5. **能够重试**：重试成本低，输入、波次和 seed 可复现，玩家能比较改动前后差异。

### 3.2 反支柱

- 不用更多常驻 HUD 解决信息不足。
- 不用随机性或隐藏规则制造“深度”。
- 不用数值膨胀、局外成长或奖励投放掩盖关卡本身缺少选择。
- 不让音效决定规则或战斗时序；静音后游戏仍完整可玩。
- 不让 AI 生成音频路径、地图坐标、数值或未经审核的玩法内容。

## 4. UI 计划

### 4.1 UI 的核心问题

V6 UI 的任务不是增加装饰，而是让玩家在正确时间看到正确信息。战斗屏幕最多保留三个一级焦点：

1. 战场与当前威胁。
2. 城堡生命、金币和波次状态。
3. 当前可执行动作：选塔、建造、升级或开波。

塔详细属性、失败统计、完整敌人组成和帮助说明不应全部常驻，应使用上下文面板、波次预览或结果页承载。

### 4.2 战斗前：部署与威胁预览

- 进入关卡时用 2–3 秒非阻塞式镜头/高亮依次标出入口、基地和塔位；玩家可立即跳过。
- 下一波卡片显示：主要敌人、数量、入口、核心威胁标签，来源必须是实际 `WavePlan`。
- 点击/触摸入口时只高亮对应路线；点击敌人图标显示简短职责，例如“速度快、生命低”，不显示无关百科。
- 选择塔后显示费用、职责、攻击范围和可建位置状态；用形状/图标/文字辅助颜色。
- 建造前提供范围预览和金币扣除预览；建造失败明确区分金币不足、位置非法和输入未命中。
- PC 保留悬停信息，移动端以一次点击选中、再次确认建造，不能把 hover 当作必要操作。

### 4.3 战斗中：轻量 HUD

- 顶部只保留生命、金币、波次和暂停；倍速与波次开始属于操作区。
- 下一波详细信息在战斗开始后折叠为短标签，避免持续遮挡战场。
- 选中塔时弹出上下文面板：等级、角色定位、当前伤害/射程/攻速、升级效果和成本。
- 新信息必须替换或折叠旧信息，禁止继续扩大战斗 HUD 高度。
- 基地低生命、金币不足、可升级等提示设置冷却时间，避免持续闪烁和提示疲劳。
- 战斗消息按优先级覆盖：致命/漏怪 > 操作错误 > 波次信息 > 教学提示；同类消息合并。

### 4.4 结算与失败复盘

结果页分为三层：

1. **结论**：胜利/失败、到达波次、剩余生命。
2. **关键事实**：首次漏怪波次、主要漏怪入口/敌人、建塔与升级数量、剩余金币。
3. **下一步**：重试同一关、进入下一关或返回地图。

建议文本只能由确定性事件和 Metrics 派生。例如：“第 5 波短路线漏过 4 个迅捷敌人”，不能无证据地说“你应该多建减速塔”。如果证据不足，只展示事实。

### 4.5 大厅、世界与关卡选择

- 首页继续只有“开始冒险”和“创意工坊”两个核心入口，设置保持右上角。
- 首页状态区只展示真实数据：最近关卡、已完成关卡、可用塔型；不虚构等级、每日任务或奖励。
- 世界卡片减少重复徽章，突出主题、完成进度和最近可玩关卡。
- 关卡选择改为清晰路线，但三星评价延后；在没有可靠评价规则前，不展示装饰性星级。
- “我的世界”和“创意工坊”遵守项目定义：前者管理自己的世界，后者发现和游玩已发布世界。内部地图工具不冒充面向玩家的 UGC 功能。

### 4.6 移动端与无障碍门

- 主要按钮以约 48dp Android / 44pt iOS 为最低触控参考，并验证实际物理尺寸。
- 正文以 16sp-equivalent、主要操作以 18sp-equivalent 作为起点；战斗常驻小字不低于 14sp-equivalent。
- 验证安全区、圆角、摄像头开孔、浏览器地址栏和底部手势区。
- 正常文本目标对比度 4.5:1，大字目标 3:1；复杂背景使用描边、遮罩或底板。
- 颜色不是唯一信息：合法/非法塔位还需形状、图标或文字差异。
- 保留 reduced motion；新增屏幕震动强度或关闭选项。关键反馈不能只靠震动或声音。
- 首轮只保证中文；若声明支持其他语言，再进行英语、日语、韩语最长字符串测试。不能用缩小字体处理溢出。

### 4.7 UI 技术边界

- 不引入新的前端框架或全局状态库。
- Game Core 仍是权威状态；UI 只读取状态并发送 `GameAction`。
- 从 `main.ts` 渐进抽出战斗 HUD 的只读 ViewModel/Presenter 和反馈协调器，不进行一次性 UI 重写。
- 保持 `ScreenFlow` 为页面导航所有者，Phaser Scene 为战场渲染所有者，DOM 为 HUD/菜单所有者。
- 建立集中 UI tokens：字体尺寸、间距、触控尺寸、面板色、强调色、动效时长和 z-index 层级，减少散落 CSS 数值。
- 所有新增 UI 状态必须覆盖：默认、hover（仅 PC）、pressed、selected、disabled、loading、error。

## 5. 玩法计划

### 5.1 V6 不扩玩法数量，先提高选择质量

现有玩家动词保持为：观察、选塔、选位、建造、升级、开波、暂停、倍速、重试。V6 的核心不是增加新按钮，而是让这些动词形成完整决策链。

每个关键决策都必须回答：

- 玩家决定前知道什么？
- 选项之间交换了什么收益？
- 结果多久可见？
- 玩家如何识别错误并恢复？

### 5.2 四塔职责必须通过关卡被证明

| 塔型 | 玩家应理解的职责 | 关卡必须提供的验证情境 | 失败信号 |
| --- | --- | --- | --- |
| basic | 低成本、稳定单体、前期覆盖 | 分散普通敌人和早期资源压力 | 永远是单位金币最优解 |
| aoe | 密集波收益高 | 汇流、紧凑出生间隔 | 对任何波次都弱于 basic |
| slow | 延长其他塔的输出窗口 | 长路线、汇流区、快敌 | 单独比较伤害导致其价值不可见 |
| heavy | 对高生命目标提供高单发 | 坦克/首领与低血杂兵混合 | 过量伤害或低攻速使其没有合理窗口 |

V6 不先改数值。先用关卡、波次和可读反馈验证职责；只有同一问题在真人、回放和模拟证据中一致出现，才修改共享配置。

### 5.3 三关设计目标

- **Easy：弯道守望**——教会入口、基地、塔位、范围、建造和升级。首局失败不得来自未预告的快敌突袭。
- **Medium：双路汇流**——要求玩家比较前线分守与汇流集中防守，至少验证两种可行投资方案。
- **Hard：错峰防线**——要求玩家处理不等长路线和错峰压力。实施前必须先找到一条真人或明确动作回放可通方案。

三关的区别必须体现在位置和投资逻辑，不以简单增加生命/数量作为唯一难度来源。

### 5.4 首局教学

采用“做一次、确认一次”的上下文教学：

1. 标记入口和基地，玩家点击确认路线。
2. 高亮一个塔位，但允许玩家选择其他合法塔位。
3. 选择 basic 并完成建造；系统确认金币变化与范围。
4. 展示第一波简报，由玩家主动开波。
5. 第一波结束后提示“新建或升级”的取舍，不强制唯一答案。

教学信息可重看、可跳过，不阻塞熟练玩家。教学完成状态属于应用层存档，不进入 Game Core。

### 5.5 纠错机制候选：拆除返还

当前错误建塔主要通过重开纠正。V6 将“拆除返还”作为待验证候选，而不是直接承诺上线：

- 使用现有受控 `sellRatio` 配置，不由 UI 或 AI 决定返还比例。
- 新增行为必须成为 canonical `GameAction`，由 Game Core 计算返还与移除结果。
- Simulator、动作回放、玩家端、结果和指标同步支持。
- UI 在确认前展示返还金额，防止误触；移动端高风险操作需要二次确认或短时撤销。
- 若试玩显示拆除让选择失去承诺感或形成频繁套利，则撤回该功能，改用建造前确认和快速重试。

### 5.6 战斗复盘与动作证据

在应用/证据层记录有限的确定性动作日志：建造、升级、候选拆除、开波及其 tick/波次。日志引用内容版本、rulesetVersion 和 seed。

用途：

- 复现真人策略并在 Headless Simulator 回放。
- 比较两次重试的关键变化。
- 区分关卡问题、数值问题与机器人策略问题。

日志不包含视觉、音频时间，也不允许客户端日志反向决定正式结果。正式胜负仍由 Game Core 状态转换计算。

### 5.7 数值验证顺序

1. 冻结 V6.0 规则和三关内容 hash。
2. 为 Easy/Medium/Hard 各建立至少一条人工动作回放。
3. 先固定数值比较不同布局/塔位，再固定地图比较波次。
4. 仅在职责无法通过内容呈现时调整塔、敌人或经济参数。
5. 每次只改一组相关参数，重新跑动作回放、机器人和真人测试。
6. 更新 `balance-baseline.json`，不得覆盖旧版本证据。

## 6. 音效计划

### 6.1 音频目标

音效不是背景装饰，而是第二条规则反馈通道。玩家不看 HUD 时，也应能区分：

- 操作已接受还是被拒绝；
- 哪类塔正在攻击；
- 敌人受到普通、重击或减速；
- 基地受损、波次开始和战斗结束；
- 当前处于大厅、部署、战斗或结算状态。

静音时所有信息必须仍可通过视觉或文字获得。

### 6.2 音频系统最小架构

使用 Phaser/Web Audio 现有能力，不引入新的运行时音频框架。新增应用层 `AudioDirector`，不进入 Game Core。

```text
Game Core semantic event / UI action
        ↓
Presentation feedback mapping
        ↓
AudioDirector
        ↓
Master ─┬─ Music
        ├─ Ambience
        ├─ Combat SFX
        └─ UI SFX
```

- `Master` 统一控制；Music、Ambience、Combat、UI 分组调节。
- 为兼容现有设置，首版将 Ambience 归入 Music、UI 归入 Effects；以后需要独立滑杆时再做设置迁移。
- 浏览器首次用户手势后解锁音频；解锁前不报错、不自动爆发补播积压声音。
- 页面隐藏/失焦时暂停或淡出音乐与环境声；恢复时平滑淡入，不重复创建音轨。
- 场景切换使用交叉淡化；同一曲目不因 UI 子页面切换而从头播放。
- 音频加载失败使用静默 fallback，不能阻止游戏或地图创建。

### 6.3 语义音频事件

| 类别 | 必须覆盖 | 设计要求 |
| --- | --- | --- |
| UI | hover（PC，可选）、按下、确认、取消、错误、面板开关 | 短、轻、低延迟；错误声不刺耳 |
| 建造 | 选择塔、合法落塔、金币不足、升级、候选拆除 | 与视觉反馈同一事件触发，不从 DOM 文本推断 |
| 塔攻击 | basic、aoe、slow、heavy 四种发射/命中身份 | 音色可辨；高频 basic 需限流 |
| 敌人 | 普通受击、重击、减速、死亡 | 不为每个敌人/每次伤害无限叠声 |
| 战场 | 入口激活、波次开始、波次结束、基地受损 | 基地受损优先级高于普通攻击声 |
| 结果 | 胜利、失败、解锁下一关 | 一次触发；页面重渲染不得重复播放 |
| 环境 | 大厅风声/火把、世界主题环境、战斗底噪 | 氛围低于关键信号，不抢占语音频段 |
| 音乐 | 大厅、部署、战斗、胜利/失败短尾奏 | 部署到战斗可用分层或淡化，不要求首版动态作曲 |

### 6.4 并发、优先级与混音预算

- 目标同时播放 voice 上限先设为 24，低端移动降级为 16；以实机性能和听感再调整。
- 优先级：基地/胜负 > UI 确认与波次 > heavy/aoe 关键反馈 > 普通攻击 > 环境装饰。
- 同类高频音效设置最小间隔并合批；不为 AOE 每个目标分别播放完整爆炸声。
- 同类连续音效使用小范围、确定性不相关的音高变化；纯表现随机不能进入 Core 或影响模拟。
- 基地受损、胜利和失败时短暂 duck 音乐/环境声，保留足够 headroom，避免削波。
- 切换设置应实时生效；主音量为 0 时不得继续创建无意义的高频 SFX 实例。

### 6.5 音频素材策略

- 运行时音频必须进入受控本地 Audio Library 和 manifest，记录来源、许可、用途、时长、循环点和响度处理。
- 不运行时请求外部 URL，不让 LLM 返回音频地址或任意文件路径。
- 首个切片只需要一套中性幻想音频包：1 首大厅循环、1 首战斗循环、1 条环境循环和约 16–24 个核心 SFX。
- 世界差异先通过环境层和少量乐器/氛围变体表达，不为每个 AI 世界生成整套未经审核音频。
- 所有循环资源检查无明显接缝；SFX 统一峰值和主观响度，避免玩家频繁调音量。
- 素材许可必须允许项目分发与修改；归属信息进入资源清单和游戏内 Credits。

### 6.6 音频设置与可访问性

- 主音量、音乐、音效三个现有滑杆接入真实输出，并增加静音快捷控制。
- 提供“降低强烈音效”选项：降低基地受损、爆炸和高频尖锐声的动态范围，不改变规则。
- 关键音频均有视觉冗余；重要屏外威胁可提供方向性视觉提示，而不是只靠声道位置。
- 屏幕震动/触觉独立开关；浏览器或设备不支持时静默降级。
- 不宣称支持空间音频、耳机模式或完整听障字幕，除非完成对应验证。

## 7. UI × 玩法 × 音效联合反馈表

| 玩家事件 | UI/视觉 | 音效 | 玩法证据 |
| --- | --- | --- | --- |
| 选择塔 | 塔卡选中、范围预览、合法塔位高亮 | 轻确认声 | 未改变 Core 状态 |
| 建造成功 | 塔出现、金币条扣除动画、建造粒子 | 建造落地声 | `towerBuilt` + 金币变化 |
| 建造失败 | 原因文本、目标短闪，不播放成功动画 | 低优先错误声 | Core 拒绝原因 |
| 升级 | 等级变化、短暂强化光、数值差异 | 金属/魔法上扬声 | `towerUpgraded` |
| 减速命中 | 敌人色调/状态图标，限制密度 | 冰霜短音，限流 | Core 状态效果事件 |
| 重炮命中 | 命中闪光、可选轻微震动 | 低频重击，优先级较高 | 实际命中与伤害事件 |
| 敌人漏过 | 基地扣血、路线/入口提示 | 警报与基地受损声，duck 音乐 | `enemyLeaked` |
| 波次开始 | 短横幅、入口激活 | 号角/鼓点 | `statusChanged: running` |
| 胜利/失败 | 结算层、关键事实 | 一次性尾奏 | GameResult |

原则：所有通道订阅同一语义事件；不得由动画结束、DOM 文本或音效回调推断游戏结果。

## 8. 技术影响与责任边界

| 模块 | V6 改动 | 禁止事项 |
| --- | --- | --- |
| `packages/core` | 可选拆除 action、必要的语义事件、动作回放输入 | 不依赖 Phaser、DOM、音频或 UI |
| `packages/shared` | canonical action/event/schema、设置版本和证据契约 | 不复制本地 DTO 变体 |
| `packages/simulator` | 回放相同 action；支持候选拆除策略 | 不做简化规则或声音逻辑 |
| `packages/metrics` | 首次漏怪、入口压力、建造/升级/拆除和资源利用指标 | 不让 LLM 生成数值 |
| `apps/game/game` | GameplayController 转发输入、读取状态/事件 | 不把规则塞进控制器 |
| `apps/game/presentation` | FeedbackDirector、AudioDirector、战场视觉/音效映射 | 不反向修改 Game Core 状态 |
| DOM UI | HUD ViewModel、上下文面板、教学、结果复盘、设置 | 不从画面状态计算胜负 |
| `apps/server` | 保存版本化动作证据/设置需要时迁移 | 不信任客户端统计替代权威结果 |
| Asset Library | 本地音频 manifest、许可、fallback | 不运行时依赖 MCP 或外部链接 |

这是现有领域内演进，不需要换引擎、ECS、全局事件总线或新的前端框架。反馈映射先围绕现有 `GameEvent` 建立窄接口；只有多个系统确实重复使用后，才提取通用反馈例程。

## 9. 实施阶段与验收门

### P0：体验基线与 UI/音频审计

交付：

- 录制当前 Easy 首局、首次失败和一次重试。
- 建立 HUD 信息清单、触控尺寸/对比度审计、音频现状清单。
- 记录 5 名目标玩家的首局行为基线；至少包含塔防新手和有经验者。
- 为 Hard 找到或证伪人工可通动作序列。

通过门：问题能被分类为规则、关卡、UI、反馈或音频，而不是笼统的“不好玩”。没有真人样本则保持 `UNVERIFIED`，不进入最终数值冻结。

### P1：一关联合体验切片

范围只包含 Easy：

- 精简 HUD、下一波卡片、塔上下文面板和结果复盘。
- 首次进入教学。
- `AudioDirector`、浏览器解锁、三组音量、核心 UI/建造/波次/受损/胜负音效。
- 建造、升级、受击、漏怪的统一反馈映射。

通过门：关闭声音仍可理解；关闭视觉装饰仍能从音效区分主要事件；新玩家无讲解完成建塔和开波。未通过时不扩到三关。

### P2：玩法决策验证

- Medium/Hard 关卡与波次迭代。
- 人工动作回放和 Metrics 补齐。
- 验证两种 Medium 可行方案。
- 小范围原型验证拆除返还；通过决策门才保留。

通过门：玩家能解释至少一次位置、塔型或升级选择；失败者能指出具体调整并重试。Hard 必须至少有一条可复现通关证据。

### P3：全流程 UI 与声音

- 大厅、世界选择、关卡路线、设置和结算风格统一。
- 大厅/部署/战斗/结算音乐状态与环境声。
- 音频资源 manifest、许可、fallback 和加载失败路径。
- PC、横屏、竖屏布局与安全区。

通过门：页面切换无音轨重复、无失控叠声；设置即时生效并持久化；无声音或加载失败不影响游玩。

### P4：移动设备、性能与可访问性

- 720×1280、1080×2400、小屏设备、桌面宽屏和 844×390 横屏矩阵。
- 至少一台约六英寸真实设备验证触控、音频解锁、后台恢复和物理字体尺寸。
- 30 分钟持续运行，记录帧率、内存、音频实例和热状态。
- reduced motion、屏幕震动关闭、静音和强烈音效降低组合测试。

通过门：高频战斗不会因音频/反馈造成明显卡顿；关键按钮无误触热点；恢复前后台后音乐和战斗状态一致。

### P5：两轮试玩与冻结

- 第一轮发现问题；只修改一组相关变量。
- 第二轮使用不同参与者复测。
- 冻结 `contentVersion`、`rulesetVersion`、音频 manifest 版本和 UI tokens 版本。
- 更新 V6 证据包与回滚说明。

通过门：达到第 10 节体验门，且全部技术门通过。否则标记 Observe/Pivot，不宣称 V6 完成。

## 10. 验收指标

### 10.1 真人体验门（建议样本，不是行业标准）

- 至少 4/5 无讲解识别入口、基地、金币和开波按钮。
- 至少 4/5 独立完成首次建塔并理解金币已扣除。
- 至少 3/5 根据下一波信息主动改变塔型、位置或升级选择，并能说出理由。
- 对发生失败的参与者，至少半数能指出具体原因并主动重试；无失败样本时此项未验证。
- Medium 至少出现两种可复现方案，而非所有玩家照同一脚本。
- 声音开启时，至少 4/5 能区分基地受损与普通命中；关闭声音后任务完成率不应因丢失关键信息而下降。

### 10.2 UI 技术门

- 战斗屏幕不超过三个一级视觉焦点。
- 新功能不增加未经折叠的永久 HUD 行。
- 关键触控目标达到设计尺寸并通过真实触控验证。
- 正常/选中/禁用/错误/加载状态有可辨识反馈。
- 目标视口无页面滚动、遮挡、溢出和安全区冲突。

### 10.3 玩法技术门

- 玩家端、动作回放和 Simulator 在相同内容、seed、action/tick 下结果一致。
- UI 展示的费用、范围、升级效果和返还金额来自相同配置/状态。
- 音频、动画、倍速和 reduced motion 不改变 Game Core 结果。
- 旧关卡/旧存档保持可读；新增字段有默认值和迁移测试。

### 10.4 音频技术门

- 首次用户手势前不触发浏览器音频错误。
- 音量设置实时生效、刷新后保持、0 音量无突发补播。
- 快速攻击压力场景不超过 voice budget，不持续削波或产生明显延迟。
- 页面隐藏/恢复、暂停/继续、重开、连续进入关卡均不重复音乐或泄漏实例。
- 任意音频缺失/解码失败时游戏仍可完整完成。

## 11. 测试与证据计划

- Vitest：UI ViewModel、设置迁移、音频优先级/限流、反馈映射、动作回放和候选拆除规则。
- Core fixtures：固定 map/WavePlan/seed/actions/ticks 的状态与结果快照。
- Playwright：首次教学、建造/升级/候选拆除、声音解锁与设置、暂停恢复、结果复盘、静音完整通关。
- 浏览器失败路径：音频资源 404、解码失败、AudioContext suspended、切后台、重复重开。
- 视觉证据：所有目标视口、文字最长值、低生命、金币不足、塔面板、结果页。
- 听觉证据：核心事件 cue sheet、并发压力录音或分析结果、循环接缝检查。
- 真人试玩：版本、设备、音量环境、背景经验、动作、停顿、误触、失败原因与重试行为。

每个实现切片运行聚焦测试，最终执行 `pnpm verify` 和全量 Playwright。浏览器模拟不能替代真实设备音频、触控和热性能证据。

## 12. 性能预算（初始候选，需实测校准）

- 目标：代表性移动设备稳定 60 FPS；最低可接受 30 FPS，不能通过降低规则 tick 规避。
- 同时音频 voice：中高端 24、低端 16。
- 高频同类 SFX：按类型设置 50–150ms 初始冷却，实际以可辨识度和录音检查调整。
- 音频首包保持小型；核心 UI/SFX 预载，音乐/环境可延迟加载。
- 战斗反馈优先降级顺序：环境装饰 → 次要粒子/浮字 → 普通命中音；基地受损、操作确认和胜负信号保留。
- 避免在战斗热路径创建无界 DOM、Tween、粒子、音频源或闭包；重复对象需要复用或有硬上限。

这些数值是工程起点，不是已经验证的设备结论。

## 13. 风险、回滚与停止条件

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| UI 越改越满 | 每个需求都新增常驻面板 | 新信息必须替换/折叠旧信息；不通过 HUD 门则拒绝合入 |
| 音效遮盖规则问题 | “更爽”但玩家仍不知道为何失败 | 静音测试与失败解释测试并行 |
| 过度迎合机器人 | bot 指标提高，真人决策没有变化 | 人工回放与真人观察优先于 bot 名称 |
| 拆除形成无风险试错 | 玩家频繁建拆或套利 | 调整/移除候选功能，不靠更多限制补洞 |
| 高频音效造成噪声与卡顿 | 多塔开火时削波、延迟、掉帧 | voice budget、优先级、合批、冷却和低端降级 |
| 浏览器音频生命周期泄漏 | 重开后音乐叠加 | 明确 owner、场景/页面生命周期和自动化恢复测试 |
| 大改 `main.ts` 引发回归 | UI 重构与功能同时变化 | 先抽只读状态/反馈接缝，保持行为，再逐屏迁移 |
| 资源许可不清 | 音效能播放但不能发行 | 受控本地库、许可清单、无许可不进入候选构建 |

回滚策略：UI 保留旧布局入口开关直到新战斗切片通过；音频系统支持全局禁用和静默 fallback；候选拆除使用 ruleset 版本隔离；新内容版本不覆盖旧对局快照。

停止扩张条件：若两轮定向修改后玩家仍不能依据威胁做出选择、解释失败或主动重试，则暂停大厅和音频扩展，回到关卡空间、波次和经济设计，不增加新塔、新敌人或局外成长。

## 17. 2026-09-22 实施记录

### 17.1 已落地的玩家体验

- Easy 首局提供四步上下文教学：观察入口/基地、选塔、在石台部署、阅读威胁后主动开波。教学可跳过并本地记忆；操作步骤不会拦截移动端战场触摸。
- 波次前展示来自实际 `WavePlan` 的名称、敌人数量与入口，不由 UI 猜测。
- 选中塔后展示职责、等级、伤害、射程、攻速、升级费用和拆除返还；所有数值读取共享配置与 Core 状态。
- 结算页展示实际漏怪、经济和动作事实；不生成无证据的策略建议。
- 建造、升级、四塔攻击、击杀、漏怪、开波、胜利与失败均接入语义音频；高频 cue 有冷却，voice 总数有硬上限。
- 设置新增全部静音、降低强烈音效和屏幕震动开关，并保持刷新后持久化。

### 17.2 玩法与架构

- `sellTower` 是 canonical `GameAction`，仅允许波次间执行；返还值由 Core 使用 `sellRatio` 计算，UI 无权决定结果。
- `GameplayController` 记录 tick、action、accepted/reason；Simulator 使用同一 Game Core 逐条验证动作回放，不创建第二套规则。
- `enemyLeaked` 事件补充敌人、入口和波次语义，用于事实型复盘和反馈，不依赖 Phaser 动画状态。
- 音频完全位于 presentation 层；加载、解码或浏览器授权失败会静默降级，绝不反馈修改 Core。

- 来源、许可、用途和本地路径记录于 `assets/library/audio/manifest.json` 与 `assets/library/audio/CREDITS.md`。
- 运行时只解析打包后的本地 URL；AI、服务器和 Core 均不能提供任意音频路径。
