# Fantasy Frontiers V5 — 从生成演示到可设计、可验证的塔防

> 状态：V5 技术切片已实现（2026-09-22）；真人试玩与商业结论仍待外部验证。
> 依据：2026-09-21 当前工作区代码、V1 设计与架构、V4 计划，以及用户转述的产品点评。
> 目标读者：项目负责人和后续开发者。用于确定下一阶段投入与技术边界，不是商业上线承诺。
> 文档模式：可玩切片计划（vertical slice）。内部项目材料；未作外部市场调研，不包含收入、留存或发行判断。

### 0.1 本轮实现快照

本文件最初是实施计划，现已同步为“方案 + 落地记录”。已完成的技术闭环包括：

- canonical `MapDraft` / `MapTemplateRevision` / `WavePlan` 契约、草稿编译及地图冲突校验；
- 桌面地图工坊（12×8 网格、基地/入口/多路径/塔位/障碍、撤销重做、导入导出、本地草稿、隔离试玩）；
- 默认关闭的编辑 API、乐观 revision 冲突、不可变模板修订和内容 hash；
- 同一 Game Core 在玩家战斗、编辑器试玩、Simulator 和 Evaluation Workflow 中消费相同 `WavePlan`；
- Easy / Medium / Hard 三个固定布局和显式波次的基准内容；
- 对局内容快照与 ruleset 版本字段；下一波敌人/入口简报；
- 可重复数值脚本与原始结果 [balance-baseline.json](./balance-baseline.json)，解释见 [balance-design.md](./balance-design.md)；
- Vitest 契约测试与 Playwright“编辑→校验→试玩→返回且不写正式进度”浏览器证据。

尚未完成且不能由代码自动伪造：第 12.2 节的两轮目标玩家试玩、真实移动设备验证、基于真人证据的最终数值冻结，以及公共 UGC 所需的身份鉴权/审核（本来就在 V5 非目标内）。因此当前结论是“可供试玩验证的 V5 候选”，不是“商业平衡已完成”。

## 1. 先说结论

这条点评的核心值得接受：项目需要证明玩家为什么选择某座塔、某个位置、某次升级，以及失败后为什么愿意再试一次。继续增加素材或生成更多世界，不能回答这些问题。

但“没有数值、地图都是 AI 随机生成的”不符合当前实现：项目已有集中配置、受控模板、地图校验、确定性战斗和模拟评估。真正缺少的是把这些基础组织成一条可靠的内容生产与玩法验证流程。

V5 的优先顺序：

1. 用现有规则手工设计一关，验证位置与投资选择是否影响结果。
2. 建最小内部地图编辑器，减少制作和调整关卡的成本。
3. 补受控波次编排、可复现数值实验和玩家可理解的战斗信息。
4. 做出一个包含 Easy / Medium / Hard 的三关基准战役。
5. 将验证过的关卡模板接入 AI 世界生成，而不是让生成数量代替质量。

**地图编辑器是生产工具，不是可玩性的直接来源。V5 的交付单位是“三关经过验证的体验 + 能再生产一关的工具链”，不是“一个编辑器页面”。**

## 2. 当前项目审查：保留什么，补什么

### 2.1 可追溯的事实

下列结论来自源码检查，不是本轮试玩或模拟实验的结果。链接相对于本文目录。

| 领域 | 已有事实与证据 | V5 要解决的缺口 |
| --- | --- | --- |
| 游戏定位 | [V1 设计](../v1/01-brief-design.md)、[架构](../v1/02-architecture.md) 已规定 Game First、共享规则、AI 仅负责语义 | 开发验收要从“展示效果”转向“玩家决策与内容质量” |
| 地图 | [maps](../../packages/maps/src/index.ts) 有 9 个模板，每个难度 3 个；`parameterize()` 将空地打乱后抽取塔位 | 模板主要定义道路，没有稳定的关键塔位设计；合法空位不一定是有意义的塔位 |
| 地图校验 | `validateMapSpec()` 检查坐标、入口路径、相邻格、重复占用、塔位冲突与最低数量 | 缺少射程覆盖、路线压力、位置价值等设计诊断；还需补道路与障碍物相交等编辑输入边界 |
| 数值 | [config.ts](../../packages/shared/src/config.ts) 集中定义 4 塔、4 敌人、经济、难度与机器人配置 | 有数值基础，不等于已有被验证的平衡设计；需要定位、假设、实验、版本记录 |
| 波次 | [Core](../../packages/core/src/index.ts) 的 `buildWave()` 按难度、波次和 seed 加权抽取敌人；出生时再选路径 | 缺少逐波设计意图、明确入口编排和压力节奏；没有独立的关卡波次契约 |
| 配置与实际行为 | `waveBudget`、`sellRatio` 在当前应用/包源码中仅有配置定义；动作契约没有卖塔 | 不能把配置字段当作已实现系统；先盘点有效参数，避免调了“无效旋钮” |
| 战斗核心 | 纯 TS `GameEngine`，固定 tick；[GameplayController](../../apps/game/src/game/gameplay-controller.ts) 驱动玩家战斗 | 这是应保留的基础，不应为了编辑器复制一套战斗逻辑 |
| 模拟与指标 | [Simulator](../../packages/simulator/src/index.ts) 已有 novice / baseline / expert、逐波记录、地图与配置快照；[Metrics](../../packages/metrics/src/index.ts) 确定性计算指标 | 机器人只是有限策略，不能代表真实玩家，也不能自动证明“好玩” |
| 指标语义 | 当前 `towerUsage` 是开火次数，`dominantTowerRatio` 由开火占比计算 | 不是建造占比、伤害占比或优势策略证明；快攻塔天然更容易提高这个值 |
| AI 生成 | [creative-workflow.ts](../../apps/server/src/creative-workflow.ts) 使用语义标签调用 `generateMap()`，生成后校验 | 问题在受控内容质量，不应通过开放 LLM 坐标/数值权限解决 |
| 存储 | [store.ts](../../apps/server/src/store.ts) 存储关卡 JSON、玩家进度与对局；玩家 `game_runs` 未保存完整关卡/规则快照 | 可编辑内容发布后需要版本隔离，不能用新地图解释旧对局 |
| 编辑器与前端 | 当前 `apps` 未发现地图编辑入口；[main.ts](../../apps/game/src/main.ts) 同时承载页面编排、战斗接入和 BoardScene | 新增独立编辑模块，按接缝抽取必要职责，不继续向入口堆逻辑 |

### 2.2 点评应转化成三个待验证问题

- **策略问题（推断）**：随机塔位与抽样波次可能让“有意义的选择”不稳定。验证：固定规则，比较人工布局与现有布局的实际决策、漏怪和重试行为。
- **反馈问题（待验证）**：玩家可能不知道下一波威胁，也不能解释失败。验证：不指导试玩，询问其判断依据，与实际事件对照。
- **生产问题（已确认基础缺口）**：没有可视化编排与发布闭环。验证：同一作者完成第二关时，是否不再修改渲染或 Core 源码。

不能从一条点评推导“所有关卡毫无乐趣”，也不能从自动化通关推导“产品已经好玩”。本轮不对具体塔强弱、真实胜率或玩家偏好下定论。

## 3. V5 玩家承诺与范围

### 3.1 要证明的体验

目标玩家假设：喜欢观察路线、配置火力、通过重试改善方案的轻策略玩家；不希望靠长线刷数值弥补失败。继续支持 PC 与移动端游玩，内部编辑器先面向桌面。

玩家承诺：**我能读懂威胁，在有限金币和固定塔位之间做取舍，并从战斗结果理解如何改善防线。**

核心循环：看路线和下一波 → 选位置与塔型 → 建造或升级 → 开波观察 → 判断缺口 → 调整防线 → 通关或带着新方案重试。

首局体验路径：

1. 进入关卡，识别入口、基地、可建位置；不要求先使用 AI。
2. 阅读首波简报，选择一个覆盖较好的位置，看到费用和射程。
3. 第一段战斗验证位置选择；后续快敌或密集敌人要求调整投资。
4. 波间可比较“再建一座”与“升级现有塔”，手动决定开波。
5. 结束后看到关键漏怪波次、类型、入口及实际资源使用；建议只陈述有数据支持的事实。
6. 用同一地图、同一波次重试，观察改动是否有效。下一关变化的是决策情境，不只是名称和颜色。

### 3.2 范围门

| 层级 | 内容 | 取舍 |
| --- | --- | --- |
| 必须 | 一关灰盒验证、内部地图编辑 MVP、三关基准战役、版本化发布、确定性测试、真人试玩 | 服务可玩性与可重复生产 |
| V5 后续必须 | 受控波次数据、下一波简报、失败复盘、数值实验报告、优质模板接入生成 | 在地图闭环稳定后实现，不绑进编辑器第一版 |
| 可延后 | 编辑器射程覆盖热图、批量操作、更丰富统计图 | 基础数值表和覆盖描边足以先验证 |
| 不做 | 公共 UGC 编辑器、协作编辑、社区审核系统、任意脚本、无限地图、复杂行为树 | 成本与核心问题不匹配 |
| 不做 | 新引擎/前端框架、ECS 重构、新素材批次、技能树、装备、抽卡、多人、商业化系统 | 不增加与本次验证无关的范围 |

继续使用 4 类塔与 4 类敌人。所有世界共享相同机制和已批准规则版本，不加入世界专属战斗规则。资源以已有本地库为准，不以新美术为验收条件。

商业模式、正式发行时间、团队人数和预算均未知；本计划不假设它们已确定。一次 V5 验证通过也不代表达到商业上线标准。

## 4. 地图编辑器怎么加，为什么这样加

### 4.1 比较三条路线

| 路线 | 优点 | 代价与限制 | 决策 |
| --- | --- | --- | --- |
| 直接编辑受校验的配置/JSON | 最快验证一关，不必先做工具 | 坐标难读，作者容易出错 | 用于 P0，记录制作与返工耗时 |
| 项目内独立的内部地图编辑器 | 复用 Phaser、投影、MapSpec 与校验；可视化迭代 | 需要草稿、试玩隔离、发布版本与回归 | 推荐 V5 主路线，P0 后进入 |
| 面向所有玩家的完整编辑器 | 可扩展创作体验 | 权限、审核、发现、兼容与移动编辑成本显著增加 | 延后，不以 UGC 平台作为本轮成功条件 |

反例：做一个像通用引擎那样支持任意触发器、脚本、敌人技能的编辑器。它看似“技术完整”，却违反固定机制边界，并会把玩法验证变成工具平台项目。

### 4.2 MVP 操作范围

编辑对象是逻辑网格，不是背景图片。第一版保留现有 12×8 尺寸，不先处理无限画布与自由缩放地图尺寸。

- 从已有模板/地图复制草稿；修改名称、难度、受控标签与设计备注。
- 放置或移动基地、入口、固定塔位和禁建障碍格。
- 选择一个入口，按四邻接格顺序绘制通往基地的路径；可共用路径尾段。
- 删除、撤销、重做；一次拖画作为一次撤销操作。
- 实时标记断路、越界、冲突及缺失引用；点击错误定位格子。
- 查看路径方向、路径长度、塔的实际射程；高级覆盖评分只作为设计诊断。
- 保存草稿、加载草稿、导入/导出带版本 JSON、一键试玩、返回编辑。
- 未通过校验不能试玩或发布；未完成的草稿可以保存，不能冒充合法 MapSpec。

路径必须保留顺序。不能只画一片道路后让最短路算法擅自决定敌人走法，否则会丢失绕行、汇合和作者意图。V5 每个入口先限制一条指定路径；不支持玩家堵路改变寻路。

“障碍”第一版仅表示禁建空间与合法性约束，不代表新增弹道遮挡、减速地形或可破坏物。道路与障碍重叠应报错；视觉河流、桥梁和废墟不自动产生新机制。

### 4.3 责任划分

新增逻辑模块，保持现有技术栈，不新增服务或框架：

- `apps/game/src/editor/`（拟新增）：编辑会话、工具命令、撤销栈、属性面板、Phaser 编辑 Scene。
- `packages/shared/src/schemas.ts`：唯一权威的草稿边界 DTO、模板版本、后续波次契约；复用已有 Coordinate / MapSpec，不再定义另一套运行时地图。
- `packages/maps`：地图校验、草稿编译、模板解析和只读设计诊断；无 DOM、网络、数据库依赖。
- `apps/server`：草稿 CRUD、版本发布、权限/开关、SQLite 事务、模板目录；客户端不得直接写正式关卡。
- `packages/core`：仍只接受合法的运行时数据，负责规则执行，不认识编辑笔刷、撤销栈和保存按钮。
- `packages/simulator` / `packages/metrics`：继续运行同一 Core、计算证据；不创建“编辑器专用战斗”。

数据流为：编辑草稿 → 校验/编译 → 合法 MapSpec → 同一 Game Core 试玩或模拟 → 审核证据 → 发布不可变模板版本 → 后端选模板创建关卡。

编辑器是独立逻辑应用，但可作为现有 Vite 应用的开发入口，例如 `/dev/maps`，按需加载。生产默认不开放入口及写 API；隐藏按钮不等于权限控制。

### 4.4 与现有战斗场景的接缝

先把 `main.ts` 中“创建一场战斗所需输入”和“结束后的处理”抽成明确接缝，保持原流程回归通过，再接编辑器。

建议战斗启动上下文区分 `campaign` 与 `editorPreview`：

- 正式战斗使用后端返回的关卡快照，完成后走既有进度保存。
- 编辑试玩使用经校验的草稿副本和明确 seed；不请求正式 `/levels/:id/start`，不调用正式结果接口、不解锁、不写玩家进度。
- 返回编辑时销毁试玩 Scene、计时器和事件订阅，恢复草稿与工具状态；战斗期间修改不能反写草稿。
- 复用 `board-projection.ts` 与可独立调用的地图渲染部分；不要求一次性拆完所有 `main.ts`，不复制整个 BoardScene。

## 5. 内容模型、存储与兼容

### 5.1 单一数据来源

以下都是拟议扩展，实施时先在 canonical schemas 中定义，再接消费端。

| 概念 | 所属层 | 必要内容与约束 |
| --- | --- | --- |
| `MapDraft` | 创作/API | ID、schemaVersion、revision、未完成的空间字段、备注；组合已有坐标/路径子结构，允许缺基地或未完成路径 |
| `MapSpec` | 运行时 | 继续使用现有合法地图结构；不装入选中格、相机、撤销记录 |
| `MapTemplateRevision` | 受控内容 | 稳定 templateId、不可变 revision、完整已验证布局、difficulty、tags、来源草稿与校验器版本 |
| 关卡发布快照 | 应用/持久化 | 稳定 levelId、内容版本、MapSpec、后续 WavePlan、rulesetVersion、内容 hash |
| 对局/模拟上下文 | 应用/证据 | 内容版本与快照、seed、规则/引擎版本、策略或动作记录；禁止只记录会变化的 levelId |

先实现能精确复用“完整布局”的模板修订，而不是把编辑好的塔位发布后再次随机抽掉。现有 `MapTemplate` 仅存路径，应扩展固定塔位/障碍或升级为完整布局定义。旧模板保持 legacy 参数化，新作者模板默认固定布局；允许的镜像变体也必须同步变换全部坐标并验证。

所有发布内容仍进入受控模板池，按难度供后端选择。草稿不能绕过模板池直接成为公众可玩内容。

### 5.2 草稿、验证、发布分开

1. 保存草稿只表示编辑工作没有丢失，不表示地图有效。
2. 试玩前编译为 MapSpec，运行完整校验；服务端对持久化/发布输入再次验证。
3. 发布必须绑定精确草稿 revision、布局 hash、规则版本与测试证据；内容变化后旧验收失效。
4. 发布生成不可变版本，修改通过“复制为新草稿”完成，不原地改已经被对局引用的地图。
5. 撤回仅影响后续选择；已创建关卡和进行中的对局继续引用原版本。

拟新增 SQLite 表：`map_drafts`、`map_template_revisions`、`level_revisions`；现有 `levels` 保留稳定 ID 和当前版本引用。对局表增加版本引用/快照字段。以服务端 SQLite 为权威，JSON 导出仅供审核与备份，不建立会与数据库互相覆盖的第二套真源。

最小 API 意图（路径为建议，尚未实现）：

- `POST /api/editor/map-drafts`、`GET /api/editor/map-drafts/:id`：创建/读取草稿。
- `PUT /api/editor/map-drafts/:id`：携带 expectedRevision 保存，版本冲突返回 409，不能默默覆盖。
- `POST /api/editor/map-drafts/:id/validate`：返回结构化 issues，包含 code、severity、字段路径/格子与说明。
- `POST /api/editor/map-drafts/:id/publish`：重新验证内容、版本和证据，在事务内生成模板修订；重复请求不产生重复版本。

开发入口默认关闭；第一阶段仅本机开发使用，禁止在公网部署无鉴权写接口。请求体大小、地图尺寸、对象数量、模拟 tick/时间均需设限。导入只接受受控 JSON，不执行代码、不接受任意文件路径或资源 URL。

### 5.3 迁移与回滚

- 不删除现有关卡或重置进度；为现有关卡创建 legacy revision，并保持 ID。
- 不复用 `completeGeneration()` 的“删除关卡再插入”流程实现编辑发布；这会涉及进度级联删除和已有对局引用。
- 旧玩家对局缺少完整快照，不能伪造历史版本。保留结果并标记历史证据不完整；迁移前暂停发布切换，处理活跃旧对局后再启用新版本。
- 新对局开局锁定内容与规则；发布新版本只影响后续开局。保留旧完成记录，但不同内容/规则版本的最佳生命与时长不能直接比较。
- 现有模拟记录已有地图和配置快照，扩展它们即可；快照不等于可执行旧规则，还需保留匹配的规则加载方式或对应构建版本。
- 使用 `schema_migrations` 做幂等增量迁移，在数据库副本验证备份恢复与重复执行；不直接实验生产数据库。
- 模板回滚通过切换后续选择的版本完成，不删历史证据。停用编辑器开关后，既有游玩路径必须可用。

## 6. 先设计三个不同的决策情境

以下是待试玩的设计提案，不是已验证关卡，也不要求先增加敌人机制。

| 基准关卡 | 地图与塔位设计 | 波次设计意图 | 玩家要学会的选择 |
| --- | --- | --- | --- |
| Easy：弯道守望 | 单入口弯道；前段、中段、基地前有不同覆盖机会；保留合法最低塔位数量 | 先普通敌人，再清楚预告快速敌人，最后组合检查 | 好位置比随便放更重要；补覆盖还是升级主火力 |
| Medium：双路汇流 | 双入口、汇流区与前线分离；共享防守位覆盖更晚，前线位只守一侧 | 分路施压后汇流密集波，再用坦克检验持续输出 | 前置分散防守还是汇流集中火力；范围塔与减速如何配合 |
| Hard：错峰防线 | 不等长双路线；长路有多次输出窗口，短路威胁更直接 | 错峰入口压力，末段明确安排已有 boss 与护送组合 | 投资长线收益还是短线兜底；什么时候增加火力、什么时候升级 |

具体坐标、数量、间隔、金币先在 P0/P3 实验后冻结，本文不把拍脑袋数字写成最终平衡表。沿用现有 6/8/10 波作为首轮比较基线，不同时更改所有变量。

每关必须附一张设计卡：教学目标、关键塔位及取舍、逐波目的、两种候选打法、预期失败原因、重试提示、seed/版本、试玩记录。

不能靠“所有好塔位都挤在一个点”“强制某种塔才能通过”伪造策略深度。至少在 Medium 关验证两种不同的可行投资方案，并检查换图后优先位置是否发生变化。

## 7. 数值设计：从配置表到实验闭环

本节规定数值工作的过程，不给未经运行验证的最终数值或平衡结论。

### 7.1 先写塔与敌人的职责

- `basic`：低成本稳定单体输出；验证前期投入效率和面对群体时的局限。
- `aoe`：密集敌人的单位金币收益；验证敌人密度、出生间隔和现有溅射范围语义。
- `slow`：用控制延长其他塔的输出时间；看团队增益，不只比较自身伤害。
- `heavy`：高单发、低频率；验证打坦克与打低血快敌的差异，以及过量伤害的损失。
- `normal / fast / tank / boss`：分别承担基础覆盖、响应窗口、持续火力与末段压力；不添加抗性/飞行等新机制。

### 7.2 先修口径，再调参数

1. 列出每个配置的消费者和单位；`waveBudget` 目前不驱动波次，不能把它当有效难度旋钮。卖塔未实现，本轮不因有 `sellRatio` 就顺带开发。
2. 将 Core 中减速持续时间等实际可调常量归入受控配置，保持原值与行为，再单独调参。
3. 明确目标选择规则：当前按已走的 `pathProgress` 排序，在不等长路线不等于“最靠近基地”。用专项案例决定是否调整；调整属于全世界共享规则变更，必须版本化，而非编辑器特判。
4. 同样记录当前 AOE 只从塔射程内候选敌人中计算溅射的语义；是否改变应单独测试，不在内容重构时偷偷更改。
5. 区分建造次数、花费占比、开火次数、实际伤害与控制收益；缺失指标由确定性事件/状态统计补齐，LLM 不自行估算填表。

### 7.3 建立数值工作表与实验记录

建议后续新增 `docs/v5/balance-design.md` 和受版本控制的基准关卡/实验清单，至少记录：

- 塔成本、伤害、攻击间隔、射程、升级成本/收益；敌人血量、速度、击杀收入、漏怪代价。
- 理论 DPS、击杀所需次数、不同路径覆盖时间；这些只是筛查，不是实际胜率模型。
- 每波生命总量、敌人类型/入口/间隔、潜在金币收入与预期投资节点；实际收入受漏怪影响。
- 实验假设、地图/波次 hash、规则/引擎版本、策略版本、seed 集合、结果引用、保留/撤回决定。

第一轮只在同一冻结规则下比较地图；第二轮固定地图比较波次；第三轮再调整塔与经济。一次修改一组有因果关系的变量。

### 7.4 复用现有 Simulator，而不是新增一套数值模拟

保留三种已有机器人，增加受控诊断策略：单一塔型、混合塔型、只建不升级、覆盖优先、指定人工打法的动作回放。它们用于发现异常，不代表人类水平标签。

- 先跑小规模固定实验集，记录耗时后再扩大；失败、超时和拒绝动作单独报告，不能当成胜负混入统计。
- 比较同一地图、同一敌人计划、同一 seed 下的方案，报告胜负、漏怪波次、生命、资源与行为差异。
- 固定波次不使用随机时，换 seed 得到相同局面不是独立样本；用不同已批准地图/波次变体形成场景集。
- 不要求 `expert` 永远比其他策略强：其有限前瞻与每波行动数量有局限，要先判断是策略盲点还是关卡问题。
- 现有 `compareRuns()` 要求配置相同，适合策略对照；跨配置实验应另设明确比较入口，不放宽现有防误比较约束。
- 当需要并存候选规则时，将规则快照作为受校验、只读的输入注入同一 Core、`fork()` 与 Simulator；禁止修改全局配置后并发实验，禁止只让模拟器使用候选规则。
- 测试界面与规则读取必须使用同一版本，避免面板显示旧价格、Core 扣新价格。

## 8. 波次编排是独立阶段，不混进地图 MVP

只改地图可保持 Core 战斗规则不变；想设计“第几波、哪个入口、什么敌人”，就必须扩展运行时内容契约。这是比画格子影响更大的部分。

拟新增 canonical `WavePlan`：由策划/代码配置受控编写，只能引用已有敌人 archetype 和地图 pathId。先用结构化表格，不开发通用时间轴或脚本系统。

- 每波明确敌人顺序、路径、相对波开始的出生 tick；同 tick 多事件使用稳定顺序。
- 如提供“类型、数量、间隔、起始 tick”的编写格式，由纯 TS 编译为统一 SpawnEvent 列表，不把两套执行逻辑放进 Core。
- 数量、tick、路径引用、波数与难度内容预算均校验；预算约束由项目代码配置定义，不由 AI 给数值。
- 将旧 `buildWave()` 与路径随机选择包装为 legacy 计划生成器，保留旧 seed 的队列和路径选择顺序；兼容测试固定旧行为。
- 新 Core 消费编译后的同一种波次计划。同步调整队列状态、构造参数、`fork()`、结果与模拟快照；不得让 Phaser 负责刷怪。
- 下一波简报读取同一计划，展示类型、数量、入口和主要威胁，不能用另一套随机过程生成“预测”。
- 保留手动开波；尚未引入自动波间计时，不用假倒计时制造紧迫感。

AI 仍只建议“汇流、快敌压力、末波重压”等语义类别，由后端匹配已审核的地图与波次组合；不允许 LLM 输出出生坐标、敌人数值或未经审批的刷怪时间表。

## 9. 对原系统的影响评估

影响等级是相对风险，不是代码行数或工期保证。

| 模块 | 地图编辑 MVP | 波次/数值闭环 | 风险控制与验证 |
| --- | --- | --- | --- |
| shared schemas | 中：草稿、模板修订、快照引用 | 高：WavePlan、规则版本、队列/证据扩展 | 单一定义、Zod 边界、旧数据适配测试 |
| maps | 中：草稿编译、固定布局模板、校验补强 | 中：地图与波次引用联合校验 | 不引入 UI；旧模板生成稳定性回归 |
| Core | 低：地图输入形状可不变 | 高：统一波次执行、规则注入、fork 继承 | 先锁定旧行为，再扩展；不复制引擎 |
| Phaser/UI | 中高：入口、编辑 Scene、试玩隔离、战斗接缝 | 中：波次预告、复盘、版本数值显示 | 桌面编辑优先；正式 PC/移动战斗回归 |
| server/SQLite | 中高：草稿、不可变版本、发布、迁移 | 中高：对局快照、规则/波次证据绑定 | 加法迁移、事务、旧进度与活跃对局保护 |
| Simulator/Metrics | 低中：直接复用合法 MapSpec，补内容引用 | 中高：新输入、诊断策略、指标口径 | 同一 Core；固定动作与 tick 对照 |
| Creative Workflow | 低：地图 MVP 不改 | 中：只选择审核后的模板/波次组合 | 保持原阶段顺序、语义权限与 fallback |
| Evaluation Agent | 低：已有评估入口可保留 | 中：报告增加版本、策略限制与新证据 | 不能修改实验数值；过期证据不能作为发布依据 |
| 主题素材 | 基本无影响 | 基本无影响 | 更换皮肤不改变地图合法性和战斗结果 |

结论：不需要推倒重写。复杂度集中在“编辑状态与运行状态隔离”“内容版本与进度兼容”“波次与规则输入统一”，而不是多画一个页面。

## 10. AI 的角色调整

保留特色，但把承诺改准确：**AI 帮玩家组织主题世界，程序从经过设计和验证的内容库中构建可玩关卡。**

推荐闭环：

1. 人工设计并验证基准关卡。
2. 用编辑器发布受控模板，附难度、空间类型、波次组合与适用规则版本。
3. Creative Workflow 继续生成世界语义；后端匹配已批准内容，应用有限变体。
4. 校验实际生成结果；几何变体未经等价性证明时重新模拟，不能沿用不匹配的报告。
5. 无匹配时回退到该难度已批准基准模板；无可用回退则结构化失败，不放宽合法性。
6. Evaluation Agent 基于 Simulator 和 Metrics 给出有证据的风险解释；批量回归不依赖在线 LLM。

“模型输出 JSON 合法”“地图校验通过”“机器人能赢”“玩家理解并愿意重试”是四层不同证据，不可互相替代。

导航命名也需记录现状偏差：项目约束规定“我的世界”负责创作管理，“创意工坊”负责发现已发布世界；当前界面/历史迭代曾把生成与评估集中在创作入口。V5 内部编辑器不以此为由恢复市场或扩建公共工坊，公开入口语义另行确认。

## 12. 验证方案：技术可用与游戏好玩分开

### 12.1 技术门

实施时扩展现有 `shared-maps`、`core`、`simulator-metrics`、`server-api`、`creative-workflow`、`gameplay-controller` 测试，新增编辑会话和迁移测试；不另换测试工具。

- 地图：所有入口通基地、四邻接、唯一 ID、合法坐标、塔位/道路/障碍无冲突、难度最低塔位、非法大小与未知引用拒绝。
- 编辑：撤销/重做、保存重载、JSON 往返、版本冲突不覆盖、失败保存不丢草稿、进入/退出试玩多次无重复监听。
- 发布：内容修改使验收失效、重复发布幂等、部分失败事务回滚、正在玩的旧版本不变、历史进度不丢。
- 规则：固定内容、seed、动作和 tick 序列下，玩家适配器与 Simulator 的状态/结果一致；叉分模拟不污染原状态。
- 波次：预告与实际一致、每个事件仅出生一次、路径存在、旧 seed 行为兼容、暂停与倍速不改变规则时间。
- AI：越权坐标/数值输出拒绝、模板回退明确、内容证据版本一致；禁用 LLM 后已有世界仍可玩。
- 浏览器：编辑→保存→试玩→返回→发布；正式世界选择→完整通关/失败→结果→重试→重载进度；保留 PC 与移动触控覆盖。

每个代码切片跑相关 Vitest/Playwright，再以 `pnpm verify` 作为最终项目检查。测试通过只能证明对应行为，不证明商业上线、真实设备性能或主观乐趣。

### 12.2 真人试玩门

建议首轮 5 名目标玩家，包含塔防新手与有经验者，记录各自背景；第二轮修正后再测，优先补不同参与者减少学习偏差。该规模只用于定性发现问题，不外推留存或总体胜率。

任务：无讲解完成 Easy；尝试 Medium；失败者同一内容重试；有经验者尝试 Hard。记录版本、设备、关卡、操作、停顿、漏怪节点与退出原因，经同意保留录屏/观察笔记。

以下是拟议内部决策门槛，不是行业标准，也不是已获得结果：

- 至少 4/5 能独立完成首次建塔和开波，并说明入口与守护目标。
- 至少 3/5 能根据下一波信息改变位置、塔型或升级选择，并说出理由；纯随机操作不算。
- 对发生失败的参与者，至少半数能提出具体改法并尝试；没有失败样本时此项为未验证，需要补挑战任务。
- 至少 3/5 在无额外奖励、无引导催促下主动选择下一关或重试；记录行为，不只问“好不好玩”。
- Medium 有两种可行方案的可复现记录；三关不能全部靠同一无思考脚本掩盖区别。单一策略偶尔通关不算失败，要看它是否普遍压倒其他选择。
- 对故意移动关键塔位或不合理投资的对照，结果能体现设计预期，玩家能观察到原因；不要求所有失误都立即失败。

### 12.3 Go / Observe / Pivot / Stop

- **Go**：技术门通过、主要试玩门通过、第二关制作流程可重复，再扩模板与 AI 复用。
- **Observe**：技术稳定但样本不足/无失败样本/玩家背景过于单一，补测，不宣布“平衡完成”。
- **Pivot**：能通关却仍普遍不看威胁、不做取舍，回到地图、波次和经济；不增加英雄、装备或素材掩盖问题。
- **Stop 扩张**：两轮针对性修正后仍无决策和重试信号，暂停编辑器高级功能与更多世界，重新评审核心体验；不是删除现有项目。

## 13. 主要风险与未决项

| 风险 | 信号 | 应对/负责人 |
| --- | --- | --- |
| 编辑器先于玩法无限膨胀 | 工具很多但没有一张人工可玩关卡 | P0 门先行；负责人冻结 MVP，删除高级编辑需求 |
| 随机塔位破坏作者布局 | 发布后重开布局变了 | 开发保证完整布局模板与 hash；先固定，再验证变体 |
| 调优迎合机器人 | bot 报告良好，真人不知道怎么选 | 策划分开看策略局限和真人证据；不以 expert 名称作背书 |
| 新旧内容覆盖进度或活跃对局 | 更新后战绩、地图或结算不一致 | 后端用不可变版本、快照、加法迁移；禁止删除再插入 |
| 共享规则出现分叉 | 试玩、模拟、正式战斗价格或波次不同 | 开发统一运行输入、fork 和读数；QA 做动作回放对照 |
| 编辑器写 API 暴露 | 未授权请求能发布模板 | 后端默认禁用；公网开放前单独评审权限与安全 |
| 缺少真实设备证据 | 浏览器模拟通过但手机操作困难 | QA 在战斗信息改动后补真实触控验证；桌面编辑不伪称移动支持 |

实施前需确认但不阻塞本方案的假设：编辑器先内部/桌面使用；可安排目标玩家试玩；暂不追加美术与商业化预算。若要求直接向所有玩家开放编辑，应重新评估范围，不能沿用本计划成本判断。

## 14. 下一步投入与交接

建议只先批准 P0：**用现有 Core 做一关固定塔位、带明确设计意图的灰盒塔防，完成一次策略对照和小规模试玩。** 记录“改一关需要多久、容易改错什么”，再确定编辑器最值得解决的操作。

交接清单：

- 策划：提交玩家承诺、关卡设计卡、波次意图和待验证假设。
- 开发：确认契约消费者、战斗接缝、发布版本和迁移策略；先隔离结构再加新行为。
- QA：准备非法地图、旧存档、重复发布、隔离试玩和确定性回放 fixtures。
- 试玩组织者：落实参与者、设备、任务与观察规则，不用满意度一句话替代行为证据。
- 项目负责人：每阶段根据证据决定继续、缩减或暂停，而不是按已堆功能数验收。

相对 V4 的变化：保留视觉与交互成果、技术栈和共享规则边界；把下一阶段重心改为关卡设计、内容编辑、数值验证与生产闭环。V4 的“不改数值”是当时视觉迭代范围，不是禁止未来受控调优；本计划本身也不授权立即修改规则。

本方案采用设计评审中的证据/假设分离、架构技能中的编辑态/运行态隔离，以及方案编写技能的范围与阶段门。未评审商业化、社交、叙事扩张或素材生产，因为它们不决定本轮核心问题。
